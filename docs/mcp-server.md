# MCP server

Status: design agreed (#104); milestone 1 in progress. Each section says
which milestone it belongs to.

A [Model Context Protocol](https://modelcontextprotocol.io) server lets an
AI assistant build circuits, test them and look at the result, at the
scale of a CPU or an NES: thousands of parts, test programs of hundreds of
thousands of ticks.

## Who it is for

1. The developer and an assistant building large designs together.
2. Coding agents working on the game itself (reproduce, verify).
3. Automated tests and CI.

It is not a player feature: no settings switch, no tutor, no install
story. That keeps the surface small and lets tools assume a file system.

## Principles

- **Few tools, large calls.** The cost that matters is the tokens the
  assistant writes and the number of round trips, not server time. One
  call builds a whole chip; one call runs a whole experiment.
- **Everything bulk also takes a file.** An assistant with a shell
  already has a programming language. Regular structures are generated by
  a script it writes; the server reads the result. There is no embedded
  scripting language.
- **Hierarchy is the scale strategy,** for layout, for tests and for
  reading: small chips, tested alone, combined.
- **Deterministic and bounded.** The same call on the same workspace
  gives the same result. Every loop has a limit (ticks, parts, bytes of
  output) and passing it is a clear error, never a hang.
- **Results are summaries.** Failures, counts and the first difference
  inline; full traces and listings go to files.

## Architecture

### One process, two hosts

The server is part of the `gate_quest` package, behind the cargo feature
`mcp` (never built for wasm). The MCP library (`rmcp`) and its async
runtime stay behind that feature.

| Host | Transport | Started by | Milestone |
|---|---|---|---|
| `gatequest-mcp` (no window) | stdio | the MCP client | 1 |
| The game, `gate_quest --mcp` | HTTP on 127.0.0.1 | the developer | 4 |

There is no second process and no private protocol between a server and
the game: MCP over HTTP is the inter-process protocol. A client that can
only spawn stdio servers but should attach to the open window can use a
generic stdio-to-HTTP proxy.

### Two tiers of tools

**Document tools** are plain functions on a `WorkspaceDocument` and
`logi_sim`: editing, layout, building, testing, tracing, import. They
never touch the Bevy `World`, so they cost no entities, routing or
visuals, and they run the same in both hosts.

**App tools** need the `World`: the visible simulation's transport, the
UI readout, and (stage 2) screenshots and input. They exist only where
an app runs.

A host implements one small trait: give me the workspace as a document,
take this document as the new workspace, and (app hosts) run this closure
on the `World`.

### How an edit reaches the editor

The ECS is the source of truth only for the circuit that is open. Chip
definitions (`CircuitLibrary`) and workspaces on disk are documents
already. One pure function does every edit:

```
apply(workspace: &mut WorkspaceDocument, batch: &Batch) -> Result<Report, Error>
```

| Target | Path |
|---|---|
| `gatequest-mcp`, or a workspace that is not open | load, `apply`, save |
| A chip definition of the open workspace | `apply`, then replace the library entry; the bridge updates instances in place |
| The open root circuit | read the ECS into a document (`HistoryWorld::snapshot`), `apply`, write back by difference (`HistoryWorld::restore`) |

Writing back by difference is what undo does: parts that did not change
keep their entities and their simulator state. The revision bump makes
the whole batch one undo step.

In the game the server runs on its own thread. A call that needs the
workspace crosses a channel to one exclusive system, which runs between
frames, so a tool call never interleaves with the player's edits. While
a gesture is in progress (`UndoHistory::hold`) the call waits. Long
document work (compiling, testing) happens on the server thread on a copy
of the document, not in the frame.

### Simulation

Tests and experiments compile the current document into a **private
`Sim`** (`sim::netlist::design_of`, as challenge checks do). They are
deterministic, run at full speed and leave the visible circuit alone.

The **visible simulation** is driven only by the `transport` tool (run,
pause, step, reset, rate, set an input), in the game host.

## Addressing

A part is named by a **path of labels**: `alu/sum` is the part labelled
`sum` inside the chip instance labelled `alu` of the circuit in question;
`alu/sum.cout` is a pin, `alu/sum.y:0..4` a bit field. Pin names, array
indices and bit ranges are those of version 6 references
(`docs/save-format.md`, "Wires and references").

- Every part made through the server gets a label, unique in its
  circuit. Element `i` of an array `fa` is labelled `fa[i]`, so arrays
  can be addressed as arrays again later (`fa[0..7].cout`).
- Parts made in the editor may have no label, or share one. Views list
  them with a short id (`#3fa2c1`, the first hex digits of the UUID, as
  many as make it unique); `#id` is accepted wherever a label is.
- A circuit is named by its definition name; `main` (or the workspace
  name) is the root.

## Tools

Seven tools in the first stage. Each takes its bulk argument inline or as
`file`.

| Tool | Tier | Milestone | Does |
|---|---|---|---|
| `workspace` | document | 1 | `list`, `open`, `new`, `save`, `status` |
| `view` | document | 1 | Text views of a circuit: outline, one part, diagnostics, stats, version 6 source |
| `edit` | document | 1 | Apply a batch of operations atomically |
| `test` | document | 2 | Run stored tests of one chip or the whole workspace |
| `run` | document | 2 | Run an experiment script on a private simulation |
| `import_rtl` | document | 3 | Verilog or Yosys JSON into chips |
| `transport` | app | 4 | Drive the visible simulation |
| `app` | app | stage 2 | UI readout (4), screenshots, actions, input |

Resources: `docs/save-format.md`, `docs/sim-v2-design.md`,
`docs/rtl-import.md`, this file, and the demos and gallery items as
examples (`demo://<id>`).

### `view`

`view {circuit, what}`. The default, `outline`, is one line per part:
label or id, kind and parameters, and for each input pin what drives it.
Arrays are folded into one line when their elements are wired alike.
Then the ports, the chips used with counts, and the build status. Large
circuits are cut at a line limit with a count of what was left out;
`filter` narrows by label prefix or kind.

`diagnostics` gives build errors with the parts involved (a
combinational loop lists its path), unconnected inputs, width mismatches
and the layout advisory. `stats` gives part counts by kind, flattened
size, state bits and logic depth.

### `edit`

```json
{
  "circuit": "alu",
  "ops": [
    {"add": [
      {"name": "a", "type": "Input", "w": 8},
      {"name": "b", "type": "Input", "w": 8},
      {"name": "fa", "use": "full_adder", "count": 8},
      {"name": "sum", "type": "Output", "w": 8}
    ]},
    {"wire": [
      ["a", "fa.A"], ["b", "fa.B"],
      ["fa[0..7].Cout", "fa[1..8].Cin"],
      ["fa.Sum", "sum"]
    ]}
  ]
}
```

Node entries and wire entries are exactly those of version 6, so the
demos are examples of the syntax and one parser serves both. Differences:

- `at` is optional. Parts without it are placed by the auto-layout
  (below). `step` defaults to a column.
- `name` becomes the label.

| Op | Meaning |
|---|---|
| `add` | Node entries. |
| `wire` | Wire entries: one source, then sinks; arrays and bit fields deal out as in version 6, with `Split`/`Merge` adapters generated. An input bit that is already driven is an error. |
| `unwire` | Sink references; removes what drives them. |
| `remove` | Parts by reference, with their wires. |
| `set` | `{"part": ref, …parameters, "label": …}`: change parameters or the label of parts. Wires to pins that no longer exist or changed width are reported and removed. |
| `layout` | Lay out the circuit again, or only the parts named. |
| `make_chip` (3) | `{"parts": [refs], "name": …}`: the editor's "make chip" (`sim/chip.rs`). |
| `expand` (3) | `{"part": ref}` or `{"circuit": name, "as": name}`: a gate-level copy of a word-level part or chip (`logi_sim::testkit::bitblast`, made hierarchical), as an editable chip. |
| `tests` (2) | Set the chip's stored tests. |

A call may hold several `{circuit, ops}` groups (`"edits": […]`), applied
in order; a circuit that does not exist is created as a definition.
Groups are applied to a copy and the copy becomes the workspace only if
every op succeeded **and** the workspace still loads (no chip inside
itself, port labels unique). A workspace that loads but does not compile
(a loop, a missing wire) is accepted, since that is a normal state while
building; the build result is in the report.

The report is short: parts and wires added and removed per circuit,
generated adapters, the build status, advisories. `dry_run` reports
without applying. An error names the group, the op and the entry
(`edits[1].ops[0].wire[2] ["a", "fa.X"]: "fa" has no input pin "X" (its
input pins: A, B, Cin)`).

### `test` and stored tests (milestone 2)

A chip carries its tests in the workspace file, so they keep running as
the design grows. A test has a `name` and one of:

| Kind | Meaning |
|---|---|
| `table`, `formula`, `sequence` | As challenge tests (`docs/save-format.md`, "Challenges"). |
| `equivalent` | `{"to": chip, "samples": n, "ticks": t, "seed": s}`: the same random inputs into both chips, every output compared each tick. This checks a gate-level chip against its word-level or imported reference. |
| `script` | A `run` script (below) with `expect` steps, inline or a file beside the manifest. |

`test {}` runs every test of every chip reachable from the root, each
chip compiled alone as a root, in parallel. `test {circuit}` runs one
chip's. The result lists only failures (the first failing case of each,
with inputs, expected and got) and a count of what passed.

Save format: an optional `tests` array on a circuit, in version 5 and
version 6. The root circuit's tests are kept beside the ECS in a
resource, since the ECS holds only parts and wires. Challenges keep their
test in the demo manifest.

### `run`: one call, one experiment (milestone 2)

```json
{
  "circuit": "cpu",
  "session": "boot",
  "steps": [
    {"load": {"part": "rom", "file": "tests/nestest.bin"}},
    {"set": {"reset": 1}}, {"ticks": 2}, {"set": {"reset": 0}},
    {"record": ["pc", "a", "x", "y", "p", "sp"], "when": "sync == 1"},
    {"compare": {"file": "tests/nestest.trace", "context": 5}},
    {"until": "pc == 0xC66E", "max_ticks": 200000},
    {"snapshot": "after_boot"},
    {"read": ["ram:0x00..0x10", "alu/sum.y"]}
  ],
  "trace": "out/boot.vcd"
}
```

| Step | Meaning |
|---|---|
| `set` | Root inputs by label. |
| `ticks` | Run that many ticks. |
| `until` | Run until an expression over signals is non-zero (`challenges::expr` syntax), at most `max_ticks`. |
| `expect` | Signals and values; a mismatch fails the run at that tick. |
| `read` | Return signals or memory ranges now. |
| `load`, `store` | Memory contents from or to a file (binary, or hex text) or inline. |
| `record` | From here on, record these signals each tick (or each tick `when` holds). |
| `compare` | Check the recorded rows against a file (one row per line, columns as recorded; a 6502 trace log after a column mapping). The run stops at the **first difference** and returns that row with `context` rows before it. |
| `snapshot`, `restore` | Save or restore the whole simulator state under a name (`Sim::export_state`). |

Signals are paths: a root port, any part's output pin, a register's
state, a memory cell or range. The result holds the `read` values, the
tick reached, why it stopped, and at most a few dozen recorded rows
(first, last, around a failure); the full record goes to `trace` as VCD
or CSV, change-only.

With `session`, the simulation and its snapshots stay alive on the
server after the call, and the next `run` with the same session
continues from there. That is how an assistant bisects to a failing
cycle without running from reset each time. A session is dropped when
its circuit changes; the next call says so.

Limits: `max_ticks` per call (default 1,000,000), recorded rows, trace
bytes, live sessions.

### `import_rtl` (milestone 3)

`import_rtl {file | text, top, into}` takes Verilog or Yosys JSON
(`docs/rtl-import.md`). For Verilog the server runs the `yosys` on
`PATH` with the script of that document (`memory -nomap` added when the
design has memories) and says so plainly when it is missing; the Nix
flake provides it. `into` is a new workspace, or the open one, where the
modules become chips (an existing chip of the same name is replaced only
with `replace`). CI tests use checked-in JSON and never need Yosys.

The intended loop for a large design: write the reference in Verilog,
import it as `x_ref`, build `x` from gates and smaller chips, store an
`equivalent` test of `x` against `x_ref`, move up a level.

## Auto-layout

Parts added without `at` are placed by `sim::layout` (layered, by logic
depth). New parts in an otherwise placed circuit are laid out as a group
beside the existing ones; `layout` redoes a whole circuit.

A layered layout of one flat circuit stops being readable long before it
stops being correct. Every edit report and `view diagnostics` carries an
advisory when a circuit passes **150 parts**: its size, and the largest
groups of parts that connect to the rest through few wires, as
candidates for `make_chip`. It is advice; nothing is refused.

Routing is the editor's job and happens only in the game host.

## Safety (milestone 4 for the game host)

- No server exists unless asked for: the `gatequest-mcp` program, or the
  game started with `--mcp`.
- The game host binds 127.0.0.1 on a free port with a random token per
  run, and writes both to `<data dir>/mcp.json` for clients to read.
- Once on, the server may open, edit and save any workspace of the data
  folder. Saves go through `WorkspaceStore` (atomic, previous save kept
  as `.bak`). Demos stay read-only until copied.
- `file` arguments are read as given; output files (`trace`, exports)
  are written under the workspace folder unless an absolute path is
  given.

## Stage 2 (designed, not scheduled)

**`app` tool.** `state` returns what the HUD shows as data: open cards,
selection, inspector fields, transport, feedback messages, the view path
(milestone 4, since it is cheap and lets tests assert on the UI).
`screenshot` renders the window or a windowless frame (centre on a part,
size, day or night) as the `screenshot` example does; it needs a GPU or
software rasteriser, which CI does not have today. `action` runs named
editor actions (select, open chip, switch tab, fit, undo, open a demo or
challenge). `input` injects pointer and key events through the real
input path, as the example's `--drag` and `--wire` do, to reproduce
gesture bugs.

**Gate-level views in the editor** (its own issue): "Open inside" on a
word-level part shows its gates, read-only, with live values. The `expand`
op is the server's hook into the same expansion.

## Milestones

1. **Document core.** `apply` with `add`, `wire`, `unwire`, `remove`,
   `set`, `layout`; label paths; `view`; `workspace`; `gatequest-mcp`
   over stdio; tests through an in-process client.
2. **Testing.** Stored tests and the save format addition; `test`;
   `run` with sessions, traces, compare and snapshots.
3. **Scale.** `import_rtl` with Yosys; `make_chip`; `expand`; the layout
   advisory's grouping; a benchmark of `apply` and `view` on a
   10,000-part workspace in `perf/`.
4. **The game as host.** `--mcp`, the exclusive system, edits by
   difference as undo steps, `transport`, `app state`.

## Testing the server

Unit tests of `apply` and `view` on documents (no feature needed, so the
default CI runs them). With the `mcp` feature, an in-process client
drives a full workflow over the real protocol: make a half adder, build a
full adder of two, view it, save it, open it again.
