# MCP server

Status: design agreed (#104). Milestones 1 to 4 (#122, #123, #124, #125)
are implemented: the batch editor with chips and gate-level expansion,
the views, stored tests, experiment scripts, Verilog import, the
`gatequest-mcp` program, and the game itself as a host (`--mcp`) with
edits as undo steps, the `transport` and the `app state` readout. Stage 2
(screenshots, UI driving, #126) is designed and not built. Each section says which milestone it belongs to;
"Running it" and "Where milestone 1 stands" are at the end.

A [Model Context Protocol](https://modelcontextprotocol.io) server lets an
AI assistant build circuits, test them and look at the result, at the
scale of a CPU or an NES: thousands of parts, test programs of hundreds of
thousands of ticks.

## Who it is for

1. The developer and an assistant building large designs together.
2. Coding agents working on the game itself (reproduce, verify).
3. Automated tests and CI.

It is not a player feature: no settings switch, no tutor, no install
story. That keeps the surface small and lets tools assume a file system.

## Principles

- **Few tools, large calls.** The cost that matters is the tokens the
  assistant writes and the number of round trips, not server time. One
  call builds a whole chip; one call runs a whole experiment.
- **Everything bulk also takes a file.** An assistant with a shell
  already has a programming language. Regular structures are generated by
  a script it writes; the server reads the result. There is no embedded
  scripting language.
- **Hierarchy is the scale strategy,** for layout, for tests and for
  reading: small chips, tested alone, combined.
- **Deterministic and bounded.** The same call on the same workspace
  gives the same result. Every loop has a limit (ticks, parts, bytes of
  output) and passing it is a clear error, never a hang.
- **Results are summaries.** Failures, counts and the first difference
  inline; full traces and listings go to files.

## Architecture

### One process, two hosts

The server is part of the `gate_quest` package, behind the cargo feature
`mcp` (never built for wasm). The MCP library (`rmcp`) and its async
runtime stay behind that feature.

| Host | Transport | The workspace is | Started by | Milestone |
|---|---|---|---|---|
| `gatequest-mcp` | stdio | a document the server holds | the MCP client | 1 |
| `gatequest-mcp --app` | stdio | open in the game's simulation layer, no window | the MCP client | 4 |
| The game, `gate_quest --mcp` | HTTP on 127.0.0.1 | the one open in the editor | the developer | 4 |

There is no second process and no private protocol between a server and
the game: MCP over HTTP is the inter-process protocol. A client that can
only spawn stdio servers but should attach to the open window can use a
generic stdio-to-HTTP proxy.

### Two tiers of tools

**Document tools** are plain functions on a `WorkspaceDocument` and
`logi_sim`: editing, layout, building, testing, tracing, import. They
never touch the Bevy `World`, so they cost no entities, routing or
visuals, and they run the same in both hosts.

**App tools** need the `World`: the visible simulation's transport, the
UI readout, and (stage 2) screenshots and input. They exist only where
an app runs.

The tools are written once, on a `Session` (`mcp/session.rs`). Without
an app the session holds its workspace itself. With one it has an
`AppLink`: read the open workspace as a document, commit a document as
its new content, replace it, save it, drive the transport, read the
state. Every tool call starts by reading the app's workspace, so the
session always works on what the editor shows now.

### How an edit reaches the editor

The ECS is the source of truth only for the circuit that is open. Chip
definitions (`CircuitLibrary`) and workspaces on disk are documents
already. One pure function does every edit:

```
apply(workspace: &mut WorkspaceDocument, batch: &Batch) -> Result<Report, Error>
```

| Target | Path |
|---|---|
| `gatequest-mcp`, or a workspace that is not open | load, `apply`, save |
| A chip definition of the open workspace | `apply`, then replace the library entry; the bridge updates instances in place |
| The open root circuit | read the ECS into a document (`HistoryWorld::snapshot`), `apply`, write back by difference (`HistoryWorld::restore`) |

Writing back by difference is what undo does: parts that did not change
keep their entities and their simulator state. The revision bump makes
the whole batch one undo step.

In the game the server runs on its own thread (`mcp/http.rs`). A call
that needs the workspace crosses a channel to one exclusive system in
`First` (`mcp/app.rs`), so it runs between frames and never interleaves
with the editor's systems. While a gesture is in progress (a mouse button
is down, or a text field holds an edit, `UndoHistory::hold`) requests
wait; a call gives up after 30 seconds. The document work of a call
(applying the batch, compiling, testing, simulating) happens on the
server thread on a copy; only the read and the commit are in a frame.

A commit names the state it was computed from. If the player edited the
circuit in between, it is refused, nothing changes, and the assistant
tries again on the new circuit.

What the session reads is the root circuit, the chips it reaches, and
the chips that came through the server (an edit, an opened workspace),
so a chip made through the server is there for the next call before it
is placed anywhere. (The editor saves only the chips
the root reaches, as it always has: place a chip before saving and
quitting. `gatequest-mcp` without `--app` saves every chip.)

### Simulation

Tests and experiments compile the current document into a **private
`Sim`** (`sim::netlist::design_of`, as challenge checks do). They are
deterministic, run at full speed and leave the visible circuit alone.

The **visible simulation** is driven only by the `transport` tool (run,
pause, step, reset, rate, set an input), in the game host.

## Addressing

A part is named by a **path of labels**: `alu/sum` is the part labelled
`sum` inside the chip instance labelled `alu` of the circuit in question;
`alu/sum.cout` is a pin, `alu/sum.y:0..4` a bit field. Pin names, array
indices and bit ranges are those of version 6 references
(`docs/save-format.md`, "Wires and references").

- Every part made through the server gets a label, unique in its
  circuit. Element `i` of an array `fa` is labelled `fa[i]`, so arrays
  can be addressed as arrays again later (`fa[0..7].cout`).
- A label made in the editor that is not a name (letters, digits, `_`)
  is used with every run of other characters as `_`: `data RAM` is
  `data_RAM`, `Out value` is `Out_value`. Views show that form.
- Parts with no label, or sharing one, are listed with a short id
  (`#3fa2c1`, the first hex digits of the UUID, as many as make it
  unique); `#id` is accepted wherever a label is.
- A circuit is named by its definition name; `main` (or the workspace
  name) is the root.

### `view`

`view {circuit, what, filter, limit}`. The default, `outline`, starts
with the circuit's size, its ports in pin order and the chips it uses
with counts. Then one line per part: how to refer to it, its kind and
parameters, and for each input pin what drives it:

```
circuit "main" (root): 13 parts + 17 generated adapters, 50 wires
ports: in A[8] B[8] Cin | out Cout Sum[8]
chips: full_adder x8
parts:
  A  Input w=8
  fa[1]  full_adder  A<-A:1  B<-B:1  Cin<-fa[0].Cout
  Sum  Output w=8  in<-{fa[0].Sum, fa[1].Sum, …}
```

Generated `Split`/`Merge` adapters are not listed; a pin fed through
them reads as the bits it gets (`A:1`, `{lo, hi}` with the low bits
first), which is how the wiring was written. Parts are cut at `limit`
lines (200) with a count of what was left out; `filter` keeps the parts
whose name or kind starts with it.

`diagnostics` gives the build result, the inputs nothing drives and the
layout advisory. `stats` gives part counts by kind and the flattened
size. `groups` lists the parts that would make chips ("Auto-layout",
below).

`compiled` compiles the circuit as a root, as tests do, and says what
the compiler made of it: every chip definition it reaches, sorted, as
`matched as …` (the word functions the function matcher replaced it
with), `not matched: …` (why not) or `not analysed` (a clock or memory is
inside it); then the program's size (instructions in total and by op,
state words, slots, memories, depth), the instruction count with
`func_match`, `lift` and `words` off, and a `compiled` test that pins the
result as it is:

```
compiled "main" as a root (2 chip definition(s) reached; the root itself is never replaced)
  full_adder: matched as [Add { a: 0, b: 1, inv_b: false, cin: In(2), carry: true }, Add { … carry: false }]
  half_adder: not matched: no cheaper: 2 vs 2
program: 39 instructions (AddCarry 8, AddSum 8, Concat 7, Shr 16), 0 state words, 43 slots, 0 memories, depth 10
without func_match, lift and words: 63 instructions
a test that pins this (edit op "tests"):
  {"name":"compiled","compiled":{"matched":["full_adder"],"instructions":{"max":39}}}
```

The circuit itself is never replaced; to see whether a chip matches,
view a circuit that places it. The text after `matched as` is the
compiler's own note.

A build error, wherever it is reported, names parts by label path as the
other tools take them: `a loop of gates with no state in it: alu/n1 ->
alu/n2 -> alu/n1`, along the loop when it is one cycle inside one
circuit, else sorted, with at most 12 names.

### `edit`

```json
{
  "circuit": "alu",
  "ops": [
    {"add": [
      {"name": "a", "type": "Input", "w": 8},
      {"name": "b", "type": "Input", "w": 8},
      {"name": "fa", "use": "full_adder", "count": 8},
      {"name": "sum", "type": "Output", "w": 8}
    ]},
    {"wire": [
      ["a", "fa.A"], ["b", "fa.B"],
      ["fa[0..7].Cout", "fa[1..8].Cin"],
      ["fa.Sum", "sum"]
    ]}
  ]
}
```

Node entries and wire entries are exactly those of version 6, so the
demos are examples of the syntax and one parser serves both. Differences:

- `at` is optional. Parts without it are placed by the auto-layout
  (below). `step` defaults to a column.
- `name` becomes the label (so `label` is not given), and every part
  gets one, not only ports and chips.
- A port cannot be an array (its label is a pin name); give one port a
  width instead.
- `use` names a chip of the workspace, or `"demo/circuit"` from the
  demos and gallery, which then joins the workspace.

| Op | Meaning |
|---|---|
| `add` | Node entries. |
| `wire` | Wire entries: one source, then sinks; arrays and bit fields deal out as in version 6, with `Split`/`Merge` adapters generated. An input bit that is already driven is an error. |
| `unwire` | Sink references; removes what drives them. |
| `remove` | Parts by reference, with their wires. |
| `set` | `{"part": ref, …parameters, "label": …, "at": …, "use": …}`, or an array of these: change parameters, the label, the position or (for a chip) the definition. Each entry is checked when it is applied: wires to pins that no longer exist or whose width no longer matches the other end are removed and reported. To change the width of a whole path, remove and add. |
| `layout` | Lay out the circuit again, or only the parts named. |
| `make_chip` (3) | `{"parts": [refs], "name": chip}`: the parts become a new chip and are replaced by one instance of it, wired the same way (the editor's "make chip", `sim/chip.rs`). Ports are named after what they connect to. |
| `copy_of` (3) | `"circuit name"`, as the first op of a chip that does not exist yet: the chip starts as a copy of that circuit. |
| `expand` (3) | `true`, references, or `{"parts": …, "deep": true}`: a word-level part is replaced by an instance of its gate-level chip, and with `deep` a chip by its gate-level copy (below). |
| `tests`, `remove_tests` (2) | Set stored tests (by name), or remove them. |

**Gate-level chips.** `expand` turns an 8-bit `Add` into an instance of
the chip `Add_8_gates`: eight `full_adder_cell`s (two `Xor`, two `And`,
one `Or`) placed as the array `fa[0..8]`, carries chained, between ports
named after the part's pins. Gate chips are built the way a person would
build them with `edit` (`mcp/chips.rs` writes the `add` and `wire` ops
and the batch editor applies them), so every part is labelled, arrays can
be addressed (`fa[3].cout`) and the chip is laid out. They are made on
first use, shared by every part of that kind and width, and are ordinary
chips that can be opened, edited and tested.

Up to 8 bits a part is an array of a cell or of 1-bit gates: word-wide
gates, `Mux`, `Switch`, `Delay`, `Register` and `DLatch` an array
`bit[0..w]` of the same kind 1 bit wide; `LtU` a chain of `ltu_cell`s
from bit 0 up; `Eq` an `Xnor` per bit and a tree of `And`; the
reductions a tree of 2-input gates. A wider part is made of 8-bit
chunks, `byte[0..k]` of the 8-bit chip (and `rest`), chained or joined by
a small tree: a 64-bit adder is eight `Add_8_gates`. No generated circuit
has more than about 30 parts. 1-bit gates, memories, wiring and chips
have no gate-level form of their own.

`{"expand": {"parts": true, "deep": true}}` expands the chips placed in
the circuit too, at any depth. The originals stay as they are, as the
word-level reference: a placed chip `alu` is pointed at a copy
`alu_gates` whose word-level parts are expanded and whose own chips are
replaced the same way. A chip with nothing to expand at any depth is left
as it is. The copy belongs to `alu`: the next expansion of `alu` finds it
and uses it when it is still the same, or makes it again in place when
`alu` (or a chip inside it) has changed, its placements keeping their
wires by port. Edits made by hand to a copy are lost then; copy it under
another name to keep them. A chip of that name that `expand` did not make
is left alone, and the copy is named `alu_gates_2`. The report says how
many parts were expanded and how many chips were made. To get the
gate-level form of a whole design and keep the original as its
reference:

```json
{"circuit": "cpu_gates", "ops": [
  {"copy_of": "cpu"},
  {"expand": {"parts": true, "deep": true}},
  {"tests": [{"name": "same as cpu", "equivalent": {"to": "cpu"}}]}
]}
```

Without `deep`, `{"expand": true}` and `{"expand": [refs]}` expand this
circuit's own parts only.

**A chip's ports.** Pins of a placed chip are numbered in the order of
its port labels, so adding, removing or renaming a port moves the
others. When an edit (or a replacing import) changes a chip's ports,
every wire on its placements stays on the port of the same label; a wire
whose port is gone or changed width is removed and reported.

A call may hold several `{circuit, ops}` groups (`"edits": […]`), applied
in order; a circuit that does not exist is created as a definition.
Groups are applied to a copy and the copy becomes the workspace only if
every op succeeded **and** the workspace still loads (no chip inside
itself, port labels unique). A workspace that loads but does not compile
(a loop, a missing wire) is accepted, since that is a normal state while
building; the build result is in the report.

The report is short: parts and wires added and removed per circuit,
generated adapters, the build status, advisories. `dry_run` reports
without applying. An error names the group, the op and the entry
(`edits[1].ops[0].wire[2] ["a", "fa.X"]: "fa" has no input pin "X" (its
input pins: A, B, Cin)`).

### `test` and stored tests (milestone 2)

A chip carries its tests in the workspace file, so they keep running as
the design grows. A test has a `name` and one of:

| Kind | Meaning |
|---|---|
| `table`, `formula`, `sequence` | As challenge tests (`docs/save-format.md`, "Challenges"), on the chip's own ports. |
| `equivalent` | `{"to": chip, "samples": n, "seed": s, "hold": k}`: the same random inputs into both chips, every output compared after every tick, both from power-on. This checks a gate-level chip against its word-level or imported reference. The chips must have the same ports. |
| `script` | A `run` script (below): it passes when no `expect`, `until` or `compare` fails. |
| `compiled` | `{"matched": [chips] or {chip: true \| "text" \| {"exactly": "text"}}, "unmatched": [chips], "instructions": {"max": n, "min": n, "exactly": n}}`, any of the three: the chips that must match (a text the match must contain, or must be), the chips that must not, and bounds on the instruction count. Every broken promise is reported. The chips named must be placed in the circuit at some depth. A test with only `matched` and `max` survives compiler improvements; `unmatched`, `min` and `exactly` pin the compiler as it is. `view compiled` prints one for the current state. |
| `unoptimized` | `{"samples": n, "seed": s, "hold": k, "off": ["func_match", "lift", "words"]}`: the chip compiled as usual against the same chip with those passes off (default: all three), the same random inputs into both from power-on, every output compared after every tick; the first difference is reported as for `equivalent`. This tests flattening, function matching and word lifting on the design itself. |

The `edit` ops `{"tests": [...]}` (set or replace by name) and
`{"remove_tests": [names]}` (or `true` for all) change them. A test is
checked when it is set: its shape, and that the ports and chips it names
exist.

`test {}` runs every test of every circuit of the workspace, each on a
fresh simulation of its chip compiled alone, side by side on the
machine's cores. `test {circuit}` runs one chip's, `name` only the tests
of that name. The result lists each failure with its first failing case,
then one line of counts and the circuits that have no tests:

```
FAILED half_adder / truth: Case 2: inputs A=0, B=1; expected Sum=1, Carry=0, got Sum=1, Carry=1.
4 of 5 tests passed in 3 circuit(s) (215 cases)
```

A failed suite is a tool error, so a client sees it as one.

Save format: `docs/save-format.md`, "Stored tests". In the game the
tests of the open workspace are kept in the `WorkspaceTests` resource
beside the ECS, which holds only parts and wires, and are written back
on save.

### `run`: one call, one experiment (milestone 2)

```json
{
  "circuit": "cpu",
  "session": "boot",
  "signals": {"pc": "core/pc.q", "a": "core/acc.q", "sync": "core/control.Fetch"},
  "steps": [
    {"load": {"part": "rom", "file": "tests/nestest.nes", "skip": 16, "length": 16384}},
    {"set": {"reset": 1}}, {"ticks": 2}, {"set": {"reset": 0}},
    {"record": ["pc", "a"], "when": "sync"},
    {"compare": {"file": "tests/nestest.log", "radix": 16, "columns": ["pc"], "context": 5}},
    {"until": "pc == 0xC66E", "max_ticks": 200000},
    {"snapshot": "after_boot"},
    {"read": ["a", "ram@0x00..0x10", "core/alu/sum.y"]}
  ],
  "trace": "out/boot.vcd",
  "max_ticks": 500000
}
```

| Step | Meaning |
|---|---|
| `set` | Root inputs by label. A value that does not fit the input is an error. |
| `poke` | Write state at once, without a tick: `{"poke": {"cpu/a": 18, "cpu/pc": "0x0400", "ram@0x1234": 5, "ram": [[4660, 5], [4661, 255]]}}`. Every net is settled from the new state before the next step; an input set before it still reaches the logic at the next tick. A value that does not fit is an error, and nothing is written. |
| `ticks` | Run that many ticks. |
| `until` | Run until an expression over signals is non-zero (`challenges::expr` syntax), at most `max_ticks`; not reaching it fails the run. |
| `expect` | Signals and values; a mismatch fails the run and says what it saw. |
| `read` | Return signals, or up to 256 words of a memory (`ram@0x00..0x10`). |
| `load` | Words into a memory, for this simulation only (below). |
| `store` | A memory's words to a file: binary, or hex text for `.hex` and `.txt`. |
| `record` | From here on, record these signals after each tick, or each tick `when` holds. |
| `compare` | Check the rows recorded from here on against expected rows (below). The run stops at the **first difference**. |
| `snapshot`, `restore` | Save or restore the whole simulator state under a name. |
| `reset` | Back to power-on. |

**Signals** are paths of labels from the circuit down: `core/alu/sum.y`
is output pin `y` of part `sum` in the chip placed as `alu` in the chip
placed as `core`. The pin may be left out when the part has one output;
`:0..4` picks bits; an `Output` or `Display` names what drives it;
`ram@0x10` is one word of a memory. Expressions take names only, so
`signals` gives paths short names; a root-level label is a name already.

**State.** `poke` writes state named as signals are, and `read`,
`expect` and expressions read it back:

- a `Register`, `Delay`, `DLatch` or `SrLatch` (`cpu/a`, `cpu/a.q`);
- a chip, or one of its outputs (`cpu/a`, `cpu/a.Q`), whose output is
  wired straight to state elements, as a register built of flip-flops is;
- an `Output` such a chip drives;
- an array of any of these as one word, element 0 lowest (`cpu/a/bit`,
  `cpu/a/bit[0..8]`);
- a memory word (`ram@0x1234`), or many words of one memory as
  `"ram": [[address, value], ...]`, the form of Tom Harte's test files.

`:lo..hi` picks bits. Inputs (`set`), gates and ROM words (`load`) are
not state, and the error says what to use. When a chip is named, the rest
of its state is sorted by what it does; each flip-flop-sized cell is
simulated alone for every input and state (at most 16 bits):

- a latch the shown one copies from (the master of a master-slave
  flip-flop) is written with the same value;
- state the output never depends on (a counter beside the register) is
  left alone;
- any other state (an edge detector's previous clock) makes the chip
  refused, and its state elements are then poked by path.

A poke holds under every compile option: with word lifting, function
matching and word cleanup on, a latch merged into a word or inside a chip
compiled as a word function is still written where the program keeps it.

```json
{"signals": {"a": "cpu/a", "pc": "cpu/pc"},
 "steps": [
   {"poke": {"pc": "0x0400", "a": 18, "cpu/p.q:0..4": 3,
             "ram": [[1024, 169], [1025, 66]]}},
   {"ticks": 2},
   {"expect": {"a": 66, "pc": "0x0402"}}
 ]}
```

Every signal of a script is resolved before anything runs, so a misspelt
name costs no simulation, and the simulation is compiled keeping exactly
those nets readable.

**Loading memories.** `{"part": memory, "file": path}` cuts a binary file
into words of the memory's width (`word_bytes`, `big_endian` to override),
or reads hex words from a `.hex` or `.txt` file; `"data": [..]` gives
words inline. `skip` drops leading words (a 16-byte iNES header),
`length` takes that many, `at` is the address of the first. Into a `Ram`
it writes the simulation's state; into a `Rom` it replaces contents for
this simulation (in every placement of the chip the ROM is in). The same
description as `"load"` in an `edit` `set` op changes the part itself, so
it is saved with the workspace: that is how a ROM gets a program for
good.

**Comparing.** `compare` takes `{"file": path}` or `{"rows": [[..]]}`.
Each expected row holds values for recorded columns; a column with no
value (`null`, or absent from the line) is not checked. In a file, values
are separated by spaces or commas and `#` starts a comment. Which column
a value belongs to is given by, in order: a `NAME:value` token whose name
is a recorded signal (`A:1F`, as CPU logs write registers); `columns`, a
list of signal names for the leading values with `null` to skip one; a
first line of signal names; else the order of the `record` step. `radix`
16 reads bare hex; `skip_lines` skips a header. The failure shows the
differing signals and the `context` rows before:

```
first difference at row 4 of tests/nestest.log (tick 31):
  a: expected 0x1F, got 0x1E
rows before it (and the differing one):
  tick 24: pc=0xC000 a=0x00
  ...
```

**Results.** The result holds what `read` and `until` saw, the first and
last five recorded rows with their count, the comparison's verdict, the
tick reached, and `ok` or `FAILED` with the step. All recorded rows go to
`trace`: a `.csv` file (tick, then the columns), or a `.vcd` file with
changes only. A failed experiment is a tool error.

**Sessions.** With `session`, the simulation, its snapshots and its
signal names stay on the server, and the next `run` with the same name
continues from there; that is how an assistant bisects to a failing
cycle without running from reset each time. A session is dropped when
the workspace changes (the next call says so), and at most eight are
kept.

**Limits.** A call runs at most `max_ticks` ticks (1,000,000 unless the
script asks for more, up to 1,000,000,000), records at most 5,000,000
rows, and reads memory files up to 64 MB. File paths are used as given,
relative to the server's working directory.

### `import_rtl` (milestone 3)

`import_rtl {file, top, into, name, replace}` takes a Verilog file
(`.v`, `.sv`) or a Yosys JSON netlist (`docs/rtl-import.md`). For
Verilog the server runs the `yosys` on `PATH`:

```
read_verilog -sv <file>; hierarchy -check -top <top>; proc; opt; memory -nomap; opt; write_json
```

(`-auto-top` without `top`). A missing Yosys is said plainly, with the
command to run by hand; a Verilog error comes back as Yosys wrote it.
The Nix flake provides Yosys. Tests that need it skip themselves where
it is not installed; the others use the checked-in JSON.

Each module becomes a circuit of word-level parts, laid out
automatically, and every part is labelled with its name in the netlist,
so its signals can be read by path. With `into: "new"` (the default when
no workspace is open) the top module is the root of a new workspace.
With `into: "open"` every module, the top one too, becomes a chip of the
open workspace; a chip that has the name of a module is an error, or
with `replace` is replaced in place, its placements keeping their wires
by port name.

The intended loop for a large design: write the reference in Verilog,
import it as `x_ref`, build `x` from gates and smaller chips, store an
`equivalent` test of `x` against `x_ref`, move up a level.

### `transport` and `app` (milestone 4)

These work only where an app runs (the game with `--mcp`, or
`gatequest-mcp --app`); elsewhere they say so.

`transport {action, ticks, hz, inputs}` drives the simulation the editor
shows. Actions: `status` (the default), `run`, `pause`, `step` (`ticks`,
default 1; it pauses first), `reset` (tick 0, inputs kept). `hz` sets the
tick rate (a number, or `"max"`) and `inputs` drives root inputs by label
(`{"En": 1}`), with any action; inputs are set before a step. The answer
is the state afterwards: `paused, tick 9, rate 10 Hz`.

`app {what: "state"}` returns what the editor shows:

```
screen: Simulating
workspace: "counter" (unsaved changes)
view: the root circuit
transport: paused, tick 9, rate 10 Hz
build: ok
undo: 2 step(s), redo: 0 step(s)
selected: "r" (Register)
signals: in En=1, out Q=7
message: Saved "counter".
```

`signals` are the root's inputs as driven and its outputs and readouts
as simulated (the Signals card). Tests and experiments belong in `test`
and `run`, which have simulations of their own and leave this one alone.

In an app, `workspace` goes through the editor: `open`, `new` and
`open_demo` replace the open circuit as the Library does (unsaved work is
refused unless `discard`), and `save` is the editor's save, with its
rules and its message. A demo the player opened read-only cannot be
edited; `open_demo` makes the editable copy.

## Auto-layout

Parts added without `at` are placed by `sim::layout` (layered, by logic
depth). New parts in an otherwise placed circuit are laid out as a group
beside the existing ones; `layout` redoes a whole circuit.

A layered layout of one flat circuit stops being readable long before it
stops being correct. Every edit report and `view diagnostics` carries an
advisory when a circuit passes **150 parts**: its size, and how many
groups of its parts would make chips. `view {"what": "groups"}` lists
them, each as the references a `make_chip` takes:

```
group 1: 50 parts, 2 nets crossing
  ["p[0..50]"]
```

A group is a set of parts connected to each other when the ports and
the widely used signals (an output that goes to more than eight parts: a
bus, a control line) are left out, of at least six parts and at most 70%
of the circuit. A circuit that is one tangle has none and is split by
function instead. It is advice; nothing is refused.

Routing is the editor's job and happens only in the game host.

## Safety

- No server exists unless asked for: the `gatequest-mcp` program, or the
  game started with `--mcp` (and built with the `mcp` feature).
- The game binds 127.0.0.1 on a free port. Every request must carry
  `Authorization: Bearer <token>`, a random token made for that run;
  without it the answer is 401. The address and the token are written to
  `mcp.json` in the game's data folder (beside `workspaces/`) and the
  address is printed at start:

  ```json
  {"url": "http://127.0.0.1:41873/mcp", "token": "…", "pid": 12345}
  ```

- Once on, the server may open, edit and save any workspace of the data
  folder, and read and write the files its tools are given paths of
  (request and script files, memory images, traces, Verilog). It runs
  `yosys` when asked to import Verilog. It runs nothing else.
- Saves go through `WorkspaceStore` (atomic, the previous save kept as
  `.bak`); in the game, through the editor's own save. Demos stay
  read-only until copied.
- An edit in the game is one undo step: `Ctrl+Z` takes back what the
  assistant did.

## Running it

```sh
cargo run -p gate_quest --features mcp --bin gatequest-mcp            # documents only
cargo run -p gate_quest --features mcp --bin gatequest-mcp -- --app   # with a simulation to drive
cargo run -p gate_quest --features mcp -- --mcp                       # the game: watch it work
```

`gatequest-mcp` speaks MCP on standard input and output and works in the
player's workspace folder; set `GATEQUEST_DATA_DIR` to a scratch folder
to keep it away from real workspaces. The game with `--mcp` opens in the
editor, prints its address and writes it with the token to `mcp.json`;
a client connects with MCP's Streamable HTTP transport and the header
`Authorization: Bearer <token>`:

```sh
claude mcp add --transport http gatequest "$(jq -r .url mcp.json)" \
  --header "Authorization: Bearer $(jq -r .token mcp.json)"
```

(The token changes with every run of the game, so this is done per run.)

The repository's `.mcp.json` starts `gatequest-mcp` for Claude Code
sessions opened in it, as the server `gatequest`. Its workspaces go in
`.gatequest/` at the repository root (ignored by git), away from the
player's own; change `GATEQUEST_DATA_DIR` there to work on real ones, or
add `"--", "--app"` to the arguments for a simulation to drive. Build
once first, since a first `cargo run` takes longer than a client waits
for a server to start:

```sh
cargo build -p gate_quest --features mcp --bin gatequest-mcp
```

The code is in `src/mcp/`: `batch.rs` (the edit function), `view.rs`,
`chips.rs` (gate-level chips), `compiled.rs` (what the compiler did,
build errors with parts named, the `compiled` and `unoptimized` tests),
`import.rs` (Verilog and netlists),
`testing.rs` (stored tests), `rig.rs` (a private simulation with signals
by name), `run.rs` (experiment scripts), `memfile.rs` (memory files),
`session.rs` (the tools as plain functions on one open workspace, its
own or an app's), `app.rs` (the app side of the link), `server.rs` (the
tools over `rmcp`) and `http.rs` (the game's HTTP endpoint). Only
`server.rs`, `http.rs` and the programs need the `mcp` feature.

## Where it stands

Done: everything listed under milestones 1 to 4 below. Known gaps, to
close in later milestones:

- A `Split` adapter made by an earlier request is not reused by a later
  one that needs the same bits; a second one is made.
- In the game, a chip that is not placed anywhere is lost when the
  workspace is saved and reopened (the editor saves what the root
  reaches).
- While the game's window is hidden or minimised its frames may stop,
  and calls wait for them.
- `app state` reads the editor's resources; it does not read the cards'
  layout or the inspector's fields.
- `record` has no "when this signal changes"; `when` takes an
  expression over the current values only.
- Stored tests are not shown in the editor.
- A circuit of the open workspace cannot be deleted or renamed, and
  resources (the format documents, the demos as examples) are not
  served yet.
- New parts in a placed circuit are laid out as one block below it;
  they are not fitted near the parts they connect to.

## Testing the server

Unit tests of the document tools (`src/mcp/tests.rs` and
`src/mcp/tests/`; no feature needed, so the default CI runs them): the
batch editor, chips and expansion (every word-level kind against its
gates, by simulation), stored tests, experiment scripts, imports, and
the app host against a headless app (an edit is one undo step, untouched
parts keep their entities and the simulation its state, requests wait
for a gesture, a stale edit is refused). With the `mcp` feature, an
in-process client drives a workflow over the real protocol, and a
by-hand HTTP client reaches a headless app through the token check. The
Verilog test runs only where Yosys is installed.
